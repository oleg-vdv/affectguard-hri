# ADR 0002: Add an `interfaces/` package not listed in the spec's repo tree

## Status

Accepted (Phase 2).

## Context

FR-1 requires perception nodes to publish a message with a specific
shape: "label + confidence + timestamp". The spec's repo tree (section
6) doesn't list a folder for this, only `core/`, `perception/`,
`actuation/`, `security/`, `sim/`, `docs/`, `tests/`,
`.github/workflows/`.

ROS 2 has no built-in message type matching that shape, and custom
`.msg` definitions can only be generated by a package that depends on
`rosidl_default_generators` via `rosidl_generate_interfaces()` in
CMake — a pure `ament_python` package (like `perception/` or `core/`)
cannot generate its own custom interfaces from inside itself.

The same problem applies to raw audio input: there's no single de facto
core ROS 2 message for a raw PCM chunk, and pulling in a community
`audio_common_msgs` dependency of uncertain availability (same category
of risk as the turtlebot3/Jazzy pairing noted in ADR 0001) wasn't
justified for one message definition.

## Decision

Add a new top-level `interfaces/` package (ament_cmake,
`rosidl_generate_interfaces`) containing `EmotionState.msg` and
`AudioChunk.msg`, and have `perception/`, `core/`, and `actuation/`
depend on it.

This is treated as a necessary consequence of FR-1's explicit message
shape, not as inventing architecture the spec left unspecified — the
spec fixes the message *content*, and this package is the only
mechanism ROS 2 provides to express that content as a typed topic.

## Alternatives considered

- **JSON string over `std_msgs/String`.** Avoids a new package
  entirely. Rejected because it pushes structural validation to
  runtime string-parsing in every subscriber, which is worse for the
  policy engine that Phase 3 will build directly on top of
  `fused_emotion_state`.
- **Reuse `diagnostic_msgs/KeyValue` or similar existing message.**
  Rejected: doesn't have a native float confidence field or a
  meaningful way to express "label", and reusing an unrelated message
  type for an unrelated purpose is exactly the kind of implicit,
  undocumented decision the spec asks to avoid.

## Consequences

- One more package to build before perception/core/actuation, but it's
  a leaf dependency (no logic, just message definitions).
- `perception/` publishes `interfaces/EmotionState` on
  `perception/video/emotion_state`, `perception/audio/emotion_state`,
  and `fused_emotion_state`; `core/`'s Phase 3 policy engine consumes
  `fused_emotion_state` using the same type.
